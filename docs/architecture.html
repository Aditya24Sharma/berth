Architecture brief

berth

A small deployment platform, built from scratch for practice. You give it a Git repository; it builds the site and puts it on the internet at its own URL. This page is the whole design before we write any code.

static sites only  ·  typescript api + go proxy  ·  runs entirely on your mac

The idea

What we are actually building

Strip Vercel down and it does one thing: it turns a commit in a repository into a URL that serves files, over and over, without anyone touching a server. Everything else it sells — preview links, instant rollback, a dashboard — falls out of doing that one thing carefully.

Doing it carefully means five jobs. Something has to accept the request to deploy. Something has to build the repo, safely, because a stranger's build script is a stranger's code running on your machine. The build output has to be stored somewhere it won't be disturbed. A server has to serve it at the right hostname. And a database has to remember all of it, so you can see what happened and undo it.

We're building all five. We're skipping the parts that would triple the work without teaching much more — see what we're deliberately not building at the end.

The pieces

Three programs, one job each

api — the control plane

A small HTTP server in TypeScript. It creates projects, accepts "deploy this repo" requests, and reports status and logs. It writes a row saying a deployment should happen and returns immediately — it never builds anything itself.

That split is deliberate. A build takes minutes; an HTTP request should take milliseconds. If the API built things directly, every deploy would be a request hanging open for four minutes, and a restart mid-build would lose the work with no record it ever started.

worker — the thing that does the work

A separate TypeScript process in a loop: look for a queued deployment, claim it, clone the repo, run npm ci && npm run build inside a Docker container, copy the output to disk, mark it ready or failed. Logs stream into the database as they're produced, so you can watch a build instead of waiting for it.

Running the build in a container isn't optional politeness. npm ci executes install scripts from the repo and everything it depends on. Uncontained, that is arbitrary code from the internet with full access to your laptop.

proxy — the front door

A Go server on one port that every visitor hits. It reads the Host header of the incoming request, works out which deployment that hostname means, and serves files from that deployment's folder. It's the only piece a visitor ever touches.

Go earns its place here specifically: this is the one component where many requests arrive at once and each one does very little, which is exactly the shape Go's concurrency model is built for. The API and worker are I/O-bound glue, where Node is comfortable.

Why the polling worker instead of a real queue. Proper systems use a dedicated queue like Redis for this. We're starting with the worker asking the database "anything queued?" every couple of seconds — it's one fewer program to run, and it works fine at one build at a time.

It will break in a specific, instructive way once we run several workers: two of them can read the same queued row at the same moment and both build it. That's a race condition, and fixing it properly (an atomic claim, then a real queue) is worth far more as a lesson learned than as a library installed on day one.

The central idea

Deployments are immutable; names are pointers

This is the one design decision that makes everything else fall into place, so it's worth slowing down on.

When a build finishes, its files are written to ~/.berth/deployments/dpl_7f3a/ and never modified again. Not on the next deploy, not on rollback, not ever. Every deployment keeps its own folder and its own permanent URL, dpl_7f3a.localhost, for as long as we keep it around.

So what does "this is the production site" mean? It's a row in a table: the name myapp points at dpl_7f3a. That's it. When you visit myapp.localhost, the proxy follows the pointer and serves whatever it currently aims at.

Now rollback stops being scary. The old build hasn't been deleted, overwritten, or rebuilt — it's sitting exactly where it was, still serving at its own URL. Rolling back means updating one row so the pointer aims at it again.

State

What the database holds

One SQLite file. SQLite is a database that lives in a single file with no server process to run — which is exactly right here, and its real limits (one writer at a time) are worth meeting firsthand rather than reading about.

Vocabulary

Terms worth learning properly

These come up constantly once you leave a single application and start building systems. Each one is defined plainly, then pinned to where you'll meet it in this project.

control plane / data plane
The split between the part that decides what should happen and the part that does it and carries real traffic. Nearly every infrastructure system is organised this way, because the two have completely different reliability needs.Here: the api is control plane; the worker and proxy are data plane. Your dashboard going down should never take a deployed site offline.
reverse proxy
A server that sits in front of other things and forwards each request to the right one. "Reverse" because a normal proxy acts for the client; this one acts for the servers.Here: our Go program. nginx, Caddy and Cloudflare are all doing a fancier version of the same job.
Host header
A line every HTTP request carries saying which hostname you asked for. Without it, one machine on one IP address couldn't tell which of a thousand sites you wanted.Here: it's the entire routing input. Host: myapp.localhost is how the proxy knows what to serve.
build artifact
The output of a build — the files you actually ship, as opposed to the source you wrote. Source is what you edit; an artifact is what runs.Here: the contents of dist/ after Vite finishes. We store the artifact and throw away the clone.
immutable
Never changed after it's created. If something needs to be different, you make a new one instead of editing the old one.Here: deployment folders. It's why rollback is instant and can't half-fail — the thing you're rolling back to was never touched.
indirection
Pointing at a thing through a name rather than gripping the thing itself, so you can swap what the name means without disturbing anyone holding it.Here: the aliases table. The famous line is that every problem in computing can be solved by another layer of indirection — this is a clean example of why.
queue & worker
A list of jobs waiting to be done, and a process that takes them one at a time. It lets slow work happen outside the request that asked for it.Here: the deployments table is the queue and our worker process drains it.
polling
Repeatedly asking "is there anything new?" on a timer. The opposite is being pushed a notification when something happens. Polling is simpler and wastes work; pushing is efficient and more machinery.Here: the worker polls the database every two seconds. Simple, and visibly wasteful once you watch it.
race condition
Two things happening at once where the outcome depends on which one happens to get there first. They're nasty because the code looks correct and fails only sometimes.Here: two workers claiming the same queued deployment. We'll hit this on purpose when we add a second worker.
atomic
Happens completely or not at all, with no observable half-done state in between.Here: claiming a job needs to be atomic, and so does the alias swap — you must never have a moment where myapp points at nothing.
idempotent
Doing it twice has the same effect as doing it once. Crucial anywhere retries exist, because a retry means you can't be sure the first attempt didn't already work.Here: re-running a build for the same commit should produce a new deployment, not corrupt the old one.
container / sandbox
An isolated environment with its own filesystem and its own view of the machine, so code inside it can't reach out and touch code outside.Here: Docker, wrapping every build. This is the difference between a deployment platform and an invitation to wipe your laptop.
state machine
A thing that can only ever be in one of a fixed set of states, with defined moves between them. Writing the states down turns "what could possibly happen?" into a picture you can check.Here: queued → building → ready or failed. Any other transition is a bug.
wildcard DNS
One rule covering every subdomain of a name at once, instead of registering each one. It's what lets a platform hand out unlimited URLs without any DNS work per deploy.Here: macOS already sends every *.localhost name to your own machine — I checked, and that's what makes per-deployment URLs work with zero setup.
webhook
A URL you hand to another service so it can call you when something happens, instead of you asking it repeatedly.Here: the M6 stretch goal — GitHub calls us on every push so deploys happen without you asking.
garbage collection
Automatically reclaiming resources nothing needs any more.Here: old deployment folders. Immutability is lovely until your disk fills up, so eventually something has to delete the builds no alias points at.

Plan

Build order

Ordered to hit the risky and unfamiliar parts first. If subdomain routing or Docker is going to fight us, I'd rather find out in the first hour than after building everything around it.

  1. Prove the routingA Go proxy serving two hardcoded folders based on hostname. Nothing else — no database, no builds. Confirms the foundation before anything is built on it.
  2. Data model and apiSQLite schema plus endpoints to create a project and queue a deployment. Deployments just sit in queued. Fully testable with curl, no Docker involved.
  3. The build workerClaim a job, clone, build inside Docker with a timeout and memory limit, stream logs to the database, copy the output to disk, set the final status.
  4. Connect themThe proxy resolves real deployment ids from the database. The first end-to-end moment: a repo URL goes in, a live site comes out.
  5. Aliases and rollbackAdd the pointer layer, promote a deployment to production, roll back to a previous one. The payoff for immutability.
  6. Dashboard and live logsA minimal web UI listing projects and deployments, with build output tailing as it happens, so you stop living in curl.
  7. StretchGitHub webhooks for automatic deploys on push, concurrent builds (and the race condition that comes with them), and garbage-collecting unreferenced deployments.

Risks

What I expect to bite us

Running strangers' code

Installing dependencies executes scripts from the repo and everything it depends on. Docker with a CPU limit, a memory limit and a hard timeout from the first build — not bolted on later.

Every framework is different

Output folders and build commands vary per tool. We store both per project and auto-detect as a fallback, rather than pretending there's a standard.

Docker isn't running

Docker Desktop is installed on your machine but currently stopped. Without a preflight check that says so plainly, this surfaces as a baffling build failure.

SQLite has one writer

Fine at our scale, and a real constraint we'll feel the moment log streaming and status updates overlap. That's the lesson, not a mistake.

Scope

What we're deliberately not building

Naming these up front is half of scoping. Each one is a real system in its own right, and each is easier to add on top of a working static pipeline than to design around from the start.

  • Server-side rendering and serverless functions. Static files only. Running deployed apps as live processes means port allocation, health checks and crash recovery — a genuinely separate project.
  • Accounts and multi-tenancy. One user, no login. Auth would be the least interesting code in the repo.
  • HTTPS. Plain HTTP on localhost. Certificate issuance and renewal is its own rabbit hole and teaches nothing about deployment.
  • A CDN or edge network. One proxy on one machine. Geographic distribution is a caching problem, not a deployment one.
  • Autoscaling and orchestration. One worker, one build at a time — until step M6, where adding a second one is the point.
